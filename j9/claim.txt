grep -n "last_timeout_check" confirms it: that variable is declared on line 2841 and never read or written again anywhere in the file. It looks like it was meant to throttle how often this loop polls (e.g. "only check the idle-ring every N ms"), but that gating logic was never wired in. The result: every single time the lock-free SPSC queue (my_queue) comes back empty — which, for any port that's filtered/timing out with no response, is the overwhelming majority of iterations — this loop fires a fresh io_uring_enter syscall with a 2ms timeout, gets -ETIME back (an "error" in strace's accounting, exactly matching your errors≈calls pattern), and loops straight back around to do it again.
Do the math: you have 1310 filtered ports that get no response at all, each waiting out its full per-port timeout with this loop spinning the whole time at one syscall per ~2ms. Over a 16-second scan that's potentially 6000–8000 syscalls from this one loop alone — which is almost exactly your observed io_uring_enter count of 6414. This loop, not the TX/RX paths, is your real bottleneck. The fixes you applied to the TX reap and RX reader didn't move the needle because they were optimizing code paths that were never the dominant cost.
Why 2ms is the wrong granularity here
This idle_ring_ptr wait isn't doing real network I/O — it's purely a sleep substitute used while waiting for the recv_reader_thread_func (a separate thread) to push data into my_queue. There's no reason this consumer loop needs sub-millisecond wake-up granularity: the actual packet arrival timestamping already happens elsewhere (in the global recv reader thread, at CQE-drain time, per your existing syn_sent_time architecture), so this loop's only two jobs are (a) move newly-queued packets into per-port processing and (b) periodically check if any port has exceeded its RTT timeout and should be retried/marked filtered. Neither of those needs a 2ms wake cadence — checking every 15–20ms is more than fine for timeout bookkeeping with no measurable accuracy loss, since your actual RTT measurement isn't gated by this loop's wake frequency at all.

auto last_timeout_check = std::chrono::steady_clock::now();

std::atomic<size_t> active_count(active_ports.size());
std::atomic<size_t> ports_in_retry{0};
bool needs_submit = false;

// Tunable: how long we're willing to sleep per idle iteration. 15ms keeps
// per-port timeout sweeps responsive (timeouts are typically >=50-100ms)
// while cutting syscall volume roughly 7-8x versus the previous 2ms wait.
constexpr auto IDLE_WAIT_NS = 15 * 1000 * 1000;   // 15 ms

while (active_count.load(std::memory_order_relaxed) > 0 && !terminate_flag) {
    RawPacket pkt_batch[32];
    size_t got = my_queue->try_dequeue_bulk(pkt_batch, 32);

    // Keep draining the queue in a tight, syscall-free loop as long as data
    // keeps coming — only fall back to the timed wait once it's genuinely
    // empty, so a burst of responses doesn't get throttled by IDLE_WAIT_NS.
    while (got == 0 && active_count.load(std::memory_order_relaxed) > 0 && !terminate_flag) {
        if (idle_ring_ok) {
            struct __kernel_timespec ts = {
                .tv_sec  = 0,
                .tv_nsec = IDLE_WAIT_NS
            };
            struct io_uring_cqe* tcqe = nullptr;
            int idle_ret = io_uring_submit_and_wait_timeout(
                idle_ring_ptr, &tcqe, 1, &ts, nullptr);
            if (idle_ret >= 0 && tcqe) io_uring_cqe_seen(idle_ring_ptr, tcqe);
        } else {
            struct __kernel_timespec ts = { .tv_sec = 0, .tv_nsec = IDLE_WAIT_NS };
            clock_nanosleep(CLOCK_MONOTONIC, 0, reinterpret_cast<struct timespec*>(&ts), nullptr);
        }
        got = my_queue->try_dequeue_bulk(pkt_batch, 32);
        break;  // re-check active_count / process whatever we got, same as before
    }

Actually — simpler and closer to your existing structure, just change the timeout constant in place without restructuring the loop:

if (idle_ring_ok) {
            struct __kernel_timespec ts = {
                .tv_sec  = 0,
                .tv_nsec = 15 * 1000 * 1000   // 15 ms — was 2 ms
            };

That one-line change (2 → 15 on line 2859) is the minimal fix and should cut this loop's syscall volume by roughly 7x on its own. If you want to go further, an adaptive backoff is better still: start at 2ms right after sending a batch (when a fast reply is likely imminent) and grow the wait toward 20-30ms the longer the queue stays empty, resetting to 2ms the moment data arrives. That gives you low latency for the common case (port replies quickly) without burning syscalls during the long tail of ports that are simply going to time out with no response at all — which, per your scan output, is 1310 out of 1313 ports, i.e. the dominant case by far.
Also: delete the dead last_timeout_check variable (line 2841) or wire it into an actual periodic-check gate if it was meant to do something — right now it's pure noise that makes the loop look more throttled than it is.
