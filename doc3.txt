# io_uring_queue_init()

A concise guide to what io_uring queue initialization does and how it looks in memory.

Summary
-------
io_uring_queue_init() sets up two shared ring buffers (Submission Queue = SQ, Completion Queue = CQ) that live in user-space virtual memory but are also accessible by the kernel. This avoids repeated slow syscall overhead by letting user and kernel communicate via shared memory (fast path).

Visual before/after
-------------------
    BEFORE:           AFTER io_uring_queue_init():
    ┌─────────┐       ┌─────────┐    ╔══════════╗
    │  You    │       │  You    │    ║  Kernel  ║
    │ (User)  │ <───> │ (User)  │    ║          ║
    │         │       │         │    ║          ║
    │ Memory  │       │ [SQ]    │────║[SQ Head] ║
    │         │       │ [CQ]    │<───║[CQ Tail] ║
    └─────────┘       └─────────┘    ╚══════════╝
        │                  │              │
        Slow:              │              │
        System Calls       │              │
        Every Time!        Fast:          │
                        Shared Memory!    │
                        (Like a           │
                        Notebook)         │

What the rings are
------------------
- SQ (Submission Queue): your program writes requests here (e.g., "send packet to port X"). Kernel reads them.
- CQ (Completion Queue): kernel writes completions here (e.g., "port X: got RST"). Your program reads them.
- Both live in user-space virtual memory but map to kernel-space structures so kernel can update indices directly.

Example code locations
----------------------
Found in functions:
- receive_response()
- thread_worker()

Typical setup snippet
---------------------
    struct io_uring ring;
    size_t queue_depth;

    if (rcv_uring_depth > 0) {
        queue_depth = rcv_uring_depth;
    } else {
        queue_depth = std::min<size_t>(128, std::max<size_t>(32, ports.size() / 4));
    }

    if (io_uring_queue_init(queue_depth, &ring, 0) < 0) {
        // handle error
    }

How queue_depth is chosen (examples)
-----------------------------------
- If scanning 1000 ports:
    ports.size() = 1000
    ports.size() / 4 = 250
    queue_depth = std::min(128, std::max(32, 250)) = 128
    -> the SQ/CQ can hold 128 entries

- If scanning 50 ports:
    ports.size() = 50
    ports.size() / 4 = 12 (integer division)
    queue_depth = std::min(128, std::max(32, 12)) = 32
    -> the SQ/CQ can hold 32 entries

Memory layout after init
------------------------
Your program's virtual memory (user-space):
```
┌─────────────────────────────────────────┐
│ Your Code & Data                        │
├─────────────────────────────────────────┤
│ SQ Ring Buffer (N entries)              │ ← you write SQ entries here
│ Each entry: "Send packet to port X"     │
├─────────────────────────────────────────┤
│ CQ Ring Buffer (N entries)              │ ← kernel writes completions here
│ Each entry: "Port X: Got RST response"  │
└─────────────────────────────────────────┘
    ↑
    │ Mapped to same physical memory
    ↓
Kernel view (kernel virtual addresses):
┌─────────────────────────────────────────┐
│ Kernel sees the SAME SQ/CQ buffers      │
│ (accessed using kernel virtual addresses)│
└─────────────────────────────────────────┘
```
Important indices
-----------------
- ring.sq.head — primarily maintained by user (which slots have been submitted)
- ring.cq.tail — updated by kernel (which completions are available)

Per-thread rings (why threads create their own)
-----------------------------------------------
In the code each worker thread often initializes its own io_uring instance:

    for (int i = 0; i < config.num_threads; ++i) {
        thread_worker(...) {
            struct io_uring send_ring;
            io_uring_queue_init(actual_send_depth, &send_ring, 0);
            // This thread now has its own "fast lane"!
        }
    }

Reasoning:
- If multiple threads each have their own SQ/CQ, they can submit and reap completions without synchronizing on a single shared ring.
- Example split:
    Thread 1: scans 192.168.1.1-50 → its SQ/CQ
    Thread 2: scans 192.168.1.51-100 → its SQ/CQ
    Thread 3: scans 192.168.1.101-150 → its SQ/CQ
- Because each thread touches its own ring, you avoid locking contention — each thread operates independently.

Final notes
-----------
- io_uring moves many operations from syscall-heavy paths into shared-memory coordination, making high-throughput I/O (or packet submission) much faster.
- Choose queue_depth according to workload: larger for higher concurrency, but bounded to reasonable defaults (here: min 32, max 128).

# io_uring_get_sqe()

Summary:
- `io_uring_get_sqe()` returns a pointer to an empty submission queue entry (SQE) in the submission ring. Treat each SQE like a blank form you fill to describe a kernel I/O operation (e.g., send a packet).
- The call itself does not execute the operation; it only gives you a slot to populate. After filling multiple SQEs you submit them together for batch execution.

Analogy — "Empty forms rack":

```
┌────────────┬────────────┬────────────┬────────────┐
│ Form Slot 0│ Form Slot 1│ Form Slot 2│ Form Slot 3│
│ [  EMPTY  ]│ [  EMPTY  ]│ [  EMPTY  ]│ [  EMPTY  ]│
└────────────┴────────────┴────────────┴────────────┘
            ↑
io_uring_get_sqe() hands you this pointer — "Fill Form Slot 1"
```

After filling some SQEs:

```
┌─────────────────────────────────┬─────────────────────────────────┐
│ Slot 0:                         │ Slot 1:                         │
│ Operation: SEND                 │ Operation: SEND                 │
│ To: 192.168.1.1:80              │ To: 192.168.1.1:443             │
│ Packet: TCP SYN                 │ Packet: TCP SYN                 │
│ Buffer: 0x7f8a1b2c3d            │ Buffer: 0x7f8a1b2c4e            │
└─────────────────────────────────┴─────────────────────────────────┘
            ↑                                    ↑
            scanner filled this!                  scanner filled this!
```

Why it matters (contrast with traditional I/O):
- Traditional synchronous approach:
  1. "Kernel, send to port 80" → wait for completion → next request
  2. "Kernel, send to port 443" → wait → next
  ...and so on for each packet.
- `io_uring` approach:
  1. Obtain and fill many SQEs (e.g., slots 0–63)
  2. Submit the whole batch once — kernel processes multiple operations with fewer syscalls/context switches
- Result: much higher throughput and lower syscall overhead for many small operations (e.g., network scanners).

# io_uring_prep_sendmsg()

What it does:
- `io_uring_prep_sendmsg()` populates an SQE with sendmsg-like parameters. When called repeatedly it enables micro-batching: prepare multiple sends, then submit them together.

Batching terms:
- Macro-batch: the overall logical set of work (example: scan 70 ports).
- Micro-batch: how many SQEs you prepare per `io_uring_submit()` (example: 16).

Example — scanning 70 ports with micro-batch size 16:

```
┌────────────────────────────────────────────────────┐
│           PORT SCAN BATCH (MACRO) = 70 ports       │
├────────────────────────────────────────────────────┤
│    IO_URING BATCH 1 (MICRO): 16 packets            │
│    prep_sendmsg() × 16 → submit() → ports 1–16     │
│                                                    │
│    IO_URING BATCH 2 (MICRO): 16 packets            │
│    prep_sendmsg() × 16 → submit() → ports 17–32    │
│                                                    │
│    IO_URING BATCH 3 (MICRO): 16 packets            │
│    prep_sendmsg() × 16 → submit() → ports 33–48    │
│                                                    │
│    IO_URING BATCH 4 (MICRO): 16 packets            │
│    prep_sendmsg() × 16 → submit() → ports 49–64    │
│                                                    │
│    IO_URING BATCH 5 (MICRO): 6 packets             │
│    prep_sendmsg() × 6  → submit() → ports 65–70    │
└────────────────────────────────────────────────────┘
```

Calculation and notes:
- 70 ports ÷ 16 per micro-batch = 4.375 → round up to 5 `io_uring_submit()` calls.
- Each submit delivers up to 16 send operations; the final submit contains the remainder.
- Tuning:
  - Increase micro-batch size to lower syscall overhead and increase throughput (at the cost of more in-flight ops and possibly higher per-operation latency).
  - Use macro-batches to bound memory and rate; split very large scans into multiple macro-batches if needed.
- `io_uring` is especially useful for workloads that issue many small network operations (scanners, proxies, high-performance servers) because it minimizes per-operation overhead.

This document explains key io_uring helpers used for high-performance packet I/O in the project. It covers:
- `io_uring_prep_sendto()` for sending ARP packets
- `io_uring_prep_recvmsg()` for receiving packets (ARP/TCP)
- `io_uring_sqe_set_data()` for associating user data with SQEs

# io_uring_prep_sendto()

Purpose
- Prepare an SQE for a `sendto` operation.
- Used for simple, fixed-format packet sends (example: ARP requests).
- Matches ARP use-case: raw AF_PACKET socket, broadcast MAC destination, fixed headers.

When used (high level)
- Called from `send_arp_request()` to send ARP requests over a raw socket.
- Sends a packet using:
  `sendto(socket, buffer, size, flags, destination, dest_len)`
  - Raw socket: AF_PACKET
  - Payload: ARP packet (Ethernet + ARP header)
  - Destination: broadcast MAC `FF:FF:FF:FF:FF:FF`

ASCII diagram (send flow)
```
┌─────────────────────────────────────────────────────┐
│ STEP 1: Setup                                       │
│   • Create AF_PACKET raw socket                     │
│   • Get source MAC/IP                               │
│   • Build ARP packet template                       │
└──────────────────────────┬──────────────────────────┘
                           │
┌──────────────────────────▼──────────────────────────┐
│ STEP 2: Send ARP Requests (sendto)                  │
│   For each target IP (in batches of 64):            │
│     1. Copy template                                │
│     2. Set target IP in ARP header                  │
│     3. io_uring_prep_sendto():                      │
│        "Send this packet to broadcast MAC"          │
│     4. Submit batch                                 │
└──────────────────────────┬──────────────────────────┘
                           │
┌──────────────────────────▼──────────────────────────┐
│ NETWORK: ARP Request Flows                          │
│   Ethernet: FF:FF:FF:FF:FF:FF → Your MAC            │
│   Payload: "Who has 192.168.1.1?"                   │
└──────────────────────────┬──────────────────────────┘
                           │
┌──────────────────────────▼──────────────────────────┐
│ STEP 3: Receive ARP Replies (recvmsg)               │
│   • Setup receive on same socket                    │
│   • Wait for replies (timeout: 1500ms)              │
│   • Parse ARP reply: "192.168.1.1 is at MAC:XX:XX"  │
└─────────────────────────────────────────────────────┘
```

Batching example
- `constexpr size_t BATCH_SIZE = 64;` — ARP batch size used in sender.
- Cost estimate for 64 ARP requests:
  - 64 × `io_uring_prep_sendto()` — (memory writes, ~10 cycles each) ≈ 640 cycles
  - 1 × `io_uring_submit()` syscall — ~1000 cycles
  - Total ≈ 1640 cycles (much faster than issuing a syscall per packet)

Why ARP uses `prep_sendto()`:
- ARP packets are simple and fixed-structure (Ethernet + ARP headers).
- Always sent to broadcast MAC; no complex addressing logic.
- `sendto()` API maps directly to "send raw buffer to destination".
- Combined with io_uring batching, this yields large performance wins.

# io_uring_prep_recvmsg()

Purpose
- Prepare an SQE for a `recvmsg` operation to receive data into a buffer.
- Used by `receive_arp_reply()` and `receive_response()` (TCP/UDP/packet replies).

Typical SQE for receiving:
```
sqe = {
    opcode: IORING_OP_RECVMSG,  // Operation: RECEIVE
    fd: recv_sock,              // Socket to listen on
    addr: buffer_addr,          // Pointer to where data will be stored
    len: buffer_size,           // Max bytes to receive
    msg_flags: 0,               // Receive flags
}
```

Examples
- For TCP response:
  ```
  sqe = io_uring_get_sqe(&ring);
  io_uring_prep_recvmsg(sqe, recv_sock, &msg, 0);
  ```
- For ARP reply:
  ```
  sqe = io_uring_get_sqe(ring);
  io_uring_prep_recvmsg(sqe, sock, &msg, 0);
  ```

Concurrency model (senders vs single receiver)
```
┌─────────────────────────────────────────────────┐
│            SEND THREADS (Multiple)              │
│  Thread 1: Send to ports 1-100                  │
│  Thread 2: Send to ports 101-200                │
│  Thread 3: Send to ports 201-300                │
│  ALL sending SYN packets...                     │
└──────────────────────┬──────────────────────────┘
                       │
┌──────────────────────▼──────────────────────────┐
│          SINGLE RECEIVE THREAD                  │
│  One io_uring_prep_recvmsg() listening          │
│  Catches ALL replies from ALL ports             │
│  Processes and routes to correct result         │
└─────────────────────────────────────────────────┘
```

Syscall comparison
- Without io_uring batching:
  - 200 packets × [select() + recv()] = 200 × 2 syscalls = 400 syscalls
- With io_uring batching:
  - 200 packets × `io_uring_submit()` = ~200 syscalls + CQE peeks (no extra syscalls) = ~200 syscalls total

# io_uring_sqe_set_data()

Purpose
- Attach a 64-bit user-data value to an SQE so that when the completion event (CQE) arrives, the caller can identify which request the CQE corresponds to.
- Critical for correlating buffers/requests in high-concurrency, zero-copy I/O.

Example: sending and associating the buffer
```
io_uring_prep_sendmsg(sqe, sock, &msgs[i], 0);  // send packet
io_uring_sqe_set_data(sqe, packets[i]);        // associate packet buffer
// On completion:
buffer = io_uring_cqe_get_data(cqe);           // get the buffer back
reuse_buffer(buffer);
```

Example: receive and indicate where to put data
```
io_uring_prep_recvmsg(sqe, recv_sock, &msg, 0);  // listen
io_uring_sqe_set_data(sqe, buffer);              // "put data HERE"
// On receive completion:
buffer = io_uring_cqe_get_data(cqe);             // know which buffer has data
```

What can be stored in `user_data`?
- A pointer to buffer: `(void*)buffer_ptr`
- An integer (encoded as a pointer): `(void*)port_number`
- A magic constant: `(void*)0xDEADBEEF`
- Pointer to a struct: `(void*)&some_struct`

Kernel behavior
- The kernel copies the 64-bit user_data verbatim into the CQE; it does not interpret its contents.
- It acts as a private "cookie" that the application can use to track state.

Why it's needed
- Buffer management: know which buffer to free/reuse.
- Result correlation: match replies to sent requests or to their metadata.
- Memory safety: avoid leaks by tracking outstanding allocations.
- Performance: enable zero-copy buffer recycling instead of allocating per I/O.

Zero-copy buffer lifecycle (illustrative)
```
for each send:
    buffer = allocate_packet();
    io_uring_prep_sendmsg(sqe, sock, ...);
    io_uring_sqe_set_data(sqe, buffer);
    io_uring_submit(ring);

on completion:
    buffer = io_uring_cqe_get_data(cqe);
    reuse_buffer(buffer);   // no allocation/deallocation per packet
```

Resource cleanup (emergency)
```
char* pending_buffer = io_uring_cqe_get_data(cqe);
delete[] pending_buffer;  // cleanup even on crash/abort
```

Memory leak example (what happens without set_data)
```
Send 1000 packets:
for (int i = 0; i < 1000; i++) {
    buffer = allocate_packet();
    io_uring_prep_sendmsg(sqe, sock, ...);
    // NO io_uring_sqe_set_data -> no way to match completions to buffers
    io_uring_submit(ring);
}
// When completions arrive, there's no reliable way to know which buffer belongs to which CQE.
// Result: 1000 buffers may be leaked.
```
# io_uring submit()

What `io_uring_submit()` does

- Submits one or more prepared SQEs (submission queue entries) to the kernel for processing.
- Typically called after preparing several SQEs in userspace so the kernel can process them in a batch.
- Returns immediately (userland is asynchronous); completions are reported later on the CQ (completion queue).

High-level flow:
1. User fills SQEs in the SQ ring (userspace writes).
2. Call `io_uring_submit(ring)` (single syscall).
3. Kernel reads all filled SQEs, starts processing them, and clears SQ slots.
4. Kernel processes requests in background and writes results to the CQ when done.

---

 Batching examples (scanner use-cases)

TCP scanning (example: batch of 16):
```c
// Fill 16 send forms
for (int i = 0; i < 16; i++) {
    io_uring_prep_sendmsg(...);  // memory write to SQE
}
io_uring_submit(send_ring);  // ONE syscall for 16 packets
```

 ARP scanning (example: batch of 64):
```c
// Fill 64 ARP send forms
for (int i = 0; i < 64; i++) {
    io_uring_prep_sendto(...);  // memory write to SQE
}
io_uring_submit(arp_ring);  // ONE syscall for 64 ARP requests
```

Practical scanner loop for 1000 ports (illustrative):
```c
for (int start = 0; start < 1000; start += 70) {
    for (int micro_batch = 0; micro_batch < 70; micro_batch += 16) {
        // Fill and submit 16 send SQEs
        for (int i = 0; i < 16; i++)
            io_uring_prep_sendmsg(...);
        io_uring_submit(send_ring);  // syscall

        // Also submit receives
        for (int i = 0; i < 16; i++)
            io_uring_prep_recvmsg(...);
        io_uring_submit(recv_ring);  // another syscall
    }
}
```

Performance comparison:
- Traditional: 1000 `sendto()` calls → 1000 syscalls + 1000 context switches.
- `io_uring` batching: 1000 packets / 16 per submit ≈ 63 submits → 63 syscalls + 63 context switches.

---

 Before / After submit (visual)

Before `submit()` (userspace only):
```
SQ Ring:
[ Form1 ][ Form2 ] ... [ Form16 ]   // Kernel not aware yet
```

After `submit()` (kernel reads and clears SQEs):
```
SQ Ring:
[ EMPTY ][ EMPTY ] ... [ EMPTY ]    // Kernel has consumed them
Kernel: Now processing 16 requests
```

Pattern: Fill → Submit → Fill → Submit → Check completions...

 Error handling & robustness

Always check the return value of `io_uring_submit()` immediately.

Example:
```c
int submitted = io_uring_submit(ring);
if (submitted < 0) {
    fprintf(stderr, "io_uring_submit failed: %s\n", strerror(errno));
    // handle error (cleanup / break / retry)
}
```

Key handling strategies:

- Prevent issues (proactive)
  - Use safe batch sizes (e.g. `IO_URING_BATCH = 16` for TCP, `BATCH_SIZE = 64` for ARP).
  - Initialize queue depth according to needs:
    ```c
    queue_depth = std::min<size_t>(128,
                     std::max<size_t>(32, ports.size() / 4));
    ```
  - Check termination flag before submitting.

- Detect issues (reactive)
  - Inspect `submit()` return value immediately.
  - Monitor timeouts (2–5 seconds, depending on ARP or TCP).
  - Track number submitted versus number completed.

- Recover from issues (robust)
  - On failures, release any pre-allocated buffers to avoid leaks.
  - Process completions to free SQ space if SQ is full.
  - Clean up partial operations and try to continue scanning if possible.
  - Emergency cleanup on crash (drain CQEs, exit queue).

- Report issues (informative)
  - Log clear error messages using `strerror(errno)`.
  - Log timeout warnings when waiting excessively for completions.

---

 Handling "SQ full" and partial submits

If the SQ becomes full, you must process completions to free space before submitting more.

Pattern:
```c
int submitted = io_uring_submit(ring);
if (submitted < 0) { /* handle error */ }

int batch_completed = 0;
struct io_uring_cqe *cqe;
while (batch_completed < submitted && !terminate_flag) {
    if (io_uring_peek_cqe(ring, &cqe) == 0) {
        // process completion
        io_uring_cqe_seen(ring, cqe);
        batch_completed++;
    }
    // optionally sleep / yield to avoid busy loop
}
```

If only a subset of `submitted` completes within a timeout, handle the partial results:
- Log how many completed vs submitted.
- Release buffers for the incomplete ones.
- Decide whether to retry or continue.

---

 Timeout handling

ARP timeout example (2s):
```c
auto start = std::chrono::steady_clock::now();
int processed = 0;
const int MAX_WAIT_MS = 2000;

while (processed < submitted && !terminate_flag) {
    auto now = std::chrono::steady_clock::now();
    auto elapsed = std::chrono::duration_cast<std::chrono::milliseconds>(now - start);
    if (elapsed.count() > MAX_WAIT_MS) {
        fprintf(stderr, "send_arp_request: Timeout waiting for send completions\n");
        break;
    }
    // check for completions...
}
```

TCP timeout example (5s):
```c
auto batch_start_time = std::chrono::steady_clock::now();
int batch_completed = 0;

while (batch_completed < submitted && !terminate_flag) {
    auto now = std::chrono::steady_clock::now();
    auto elapsed_ms = std::chrono::duration_cast<std::chrono::milliseconds>(now - batch_start_time).count();
    if (elapsed_ms > 5000) {
        fprintf(stderr, "Timeout waiting for send completions\n");
        // Clean up unfinished packets & release buffers
        for (int i = batch_completed; i < submitted; ++i)
            pool.release(packets[i]);
        break;
    }
    // check for completions...
}
```

---

 Resource cleanup on submit failure

Example pattern when building or submitting fails:
```c
if (!build_success) {
    pool.release(packet);
    packets[i] = NULL;
    for (size_t j = 0; j < i; ++j)
        if (packets[j]) { pool.release(packets[j]); packets[j]=NULL; }
    return -1;
}

if (submitted < 0) {
    fprintf(stderr, "io_uring_submit failed...\n");
    for (size_t j = start; j < end; ++j) {
        if (packets[j]) { pool.release(packets[j]); packets[j] = NULL; }
    }
    break;
}
```

---

 Emergency cleanup

On termination/crash, try to clean pending operations and exit rings gracefully:
```c
void emergency_cleanup(std::vector<io_uring*> rings_to_exit) {
    for (io_uring* ring : rings_to_exit) {
        if (!ring) continue;
        struct io_uring_cqe *cqe;
        while (io_uring_peek_cqe(ring, &cqe) == 0) {
            io_uring_cqe_seen(ring, cqe);
        }
        io_uring_queue_exit(ring);
    }
}
```
Wrap with try/catch or equivalent to avoid throwing further errors during cleanup.

---

 Graceful termination checks

Always check `terminate_flag` in loops that:
- Prepare and submit SQEs.
- Wait for completions.
That allows the scanner to stop promptly and free resources.

---

 Recommended scanner submit strategy (summary)

1. Proactive:
   - Use appropriate batch sizes (`TCP=16`, `ARP=64`).
   - Allocate a queue depth that scales with load (e.g. 32–128).
   - Check termination before submitting.

2. Detect:
   - Check `io_uring_submit()` return value.
   - Track `submitted` vs `completed`.
   - Use timeouts (2s for ARP, 5s for TCP as examples).

3. Recover:
   - Release buffers on failures (no leaks).
   - Process completions to free SQ space.
   - Clean up partial submissions and continue where possible.

4. Report:
   - Log error messages with `strerror(errno)`.
   - Log timeout and partial-completion warnings.

---

 Quick checklist before adding a new submit flow

- [ ] Confirm batch size does not exceed SQ depth.
- [ ] Confirm you release buffers on every error path.
- [ ] Add timeout guard when waiting for completions.
- [ ] Add termination checks in all loops.
- [ ] Add clear logging for submit failures and timeouts.

# io_uring_peek_cqe()

## 1. What `io_uring_peek_cqe()` does

- Checks for a completion queue entry (CQE) without blocking.
- Intended for tight polling loops where you want to avoid syscalls.
- Returns immediately:
  - 0 when a CQE is available (success).
  - -EAGAIN when no completion is present (normal).
  - Other negative values indicate errors.

High-level behavior:
1. Read a memory location (CQ tail/head) to see if a completion exists.
2. If present, return a pointer to the CQE for processing.
3. No syscall is performed when there is no completion — only memory reads.

---

## 2. Basic usage patterns

Main receive loop (peek, process, acknowledge):
```c
struct io_uring_cqe *cqe;
if (io_uring_peek_cqe(&ring, &cqe) == 0) {
    // Packet received — process it
    int bytes = cqe->res;
    process_packet(...);
    io_uring_cqe_seen(&ring, cqe); // acknowledge completion
} else {
    // No packet yet — continue loop or do other work
}
```

ARP send completion loop (wait-with-polling + sleep):
```c
int processed = 0;
while (processed < submitted && !terminate_flag) {
    struct io_uring_cqe *cqe;
    if (io_uring_peek_cqe(ring, &cqe) == 0) {
        // Send completed
        if (cqe->res < 0) {
            std::cerr << "ARP send failed: " << strerror(-cqe->res) << "\n";
        }
        io_uring_cqe_seen(ring, cqe);
        processed++;
    } else {
        // No completion yet — back off a bit to avoid busy-spin
        std::this_thread::sleep_for(std::chrono::microseconds(sleep_us));
    }
}
```

---

## 3. What `peek_cqe()` actually does (conceptual)

CQ memory layout (conceptual):
```
CQ Ring:
[ Result1 ][ Result2 ][ Empty ] ...
            ^
            tail/head pointer checked by peek_cqe()
```

Pseudo-implementation:
```c
int io_uring_peek_cqe(struct io_uring *ring, struct io_uring_cqe **cqe_ptr) {
    if (ring->cq.khead != ring->cq.ktail) {
        *cqe_ptr = &ring->cq.cqes[ring->cq.khead & ring->cq.kring_mask];
        return 0;   // completion found
    }
    return -EAGAIN; // no completion, no syscall
}
```
- Important: this is a memory-only check — no syscall when no completions exist.

---

## 4. Wait-mode vs Peek-mode (latency vs CPU)

- Wait mode (blocking): sleep until a completion arrives → higher latency when used incorrectly (example: 10 ms).
- Peek mode (polling): check frequently (example: every 1 ms) → lower latency but needs controlled backoff to avoid CPU burn.
- Scanner typical compromise: short sleep between peeks (e.g., 100–1000 µs) depending on load.

---

## 5. Monitoring multiple rings

Typical scanner uses separate rings for different purposes:
- send_ring: completions for send operations
- recv_ring: completions for receive operations

Use `io_uring_peek_cqe()` on each ring without blocking, so you can:
- Handle send completions (free buffers, check errors).
- Handle receive completions (process packets, resubmit receives).
- Avoid being blocked waiting on one ring while the other has work.

Pattern:
```c
// check send ring
if (io_uring_peek_cqe(send_ring, &cqe) == 0) { handle_send(cqe); io_uring_cqe_seen(send_ring, cqe); }

// check recv ring
if (io_uring_peek_cqe(recv_ring, &cqe) == 0) { handle_recv(cqe); io_uring_cqe_seen(recv_ring, cqe); }
```

---

## 6. Pooling loop (common scanner pattern)

A typical polling loop that processes CQEs, checks timeouts, resubmits receives, and yields CPU:
```c
while (!port_states.empty() && !terminate_flag) {
    struct io_uring_cqe *cqe;

    // 1) Non-blocking peek + process
    if (io_uring_peek_cqe(&ring, &cqe) == 0) {
        process_packet(cqe);
        io_uring_cqe_seen(&ring, cqe);

        // Immediately resubmit receive
        io_uring_prep_recvmsg(...);
        io_uring_submit(&ring);
    }

    // 2) Check port/timeouts
    check_port_timeouts();

    // 3) Tiny sleep to avoid 100% CPU
    std::this_thread::sleep_for(std::chrono::microseconds(1000));
}
```

---

## 7. Return codes — how to interpret them

- 0: success — `cqe` now points to completion data. Use `cqe->res` and `io_uring_cqe_get_data(cqe)`.
- -EAGAIN: no completion yet — not an error, just retry after a small delay or handle other work.
- other negative: a real error (ring corruption, misuse). Log and handle:
```c
int ret = io_uring_peek_cqe(&ring, &cqe);
if (ret < 0 && ret != -EAGAIN) {
    std::cerr << "peek_cqe error: " << strerror(-ret) << "\n";
    // take remedial action
}
```

---

## 8. Performance implications

1. Traditional (select/poll):
   - Each check usually invokes a syscall even if no data is ready → high syscall overhead.

2. `io_uring_peek_cqe()` approach:
   - Checking for completions is a memory read — zero syscall when idle.
   - Allows frequent checks (low latency) with minimal syscall cost.
   - Use short sleeps/backoff to balance latency vs CPU.

Benefits:
- Zero-syscall completion checks when idle.
- Non-blocking: can send and receive concurrently.
- Lower latency (ms-level checks vs longer waits).
- CPU-efficient if small sleeps are used when idle.
- Scales to multiple rings.

---

## 9. Practical advice & pitfalls

- Always call `io_uring_cqe_seen()` after processing a CQE to advance the head and free CQ slots.
- Avoid busy-spin: add micro-sleeps (100–1000 µs) when no work is available.
- Tune sleep/backoff according to environment and latency requirements.
- Monitor `cqe->res` for per-request errors and act accordingly (release buffers, log error).
- When monitoring multiple rings, check all rings each iteration to avoid starving any ring.
- If you need blocking waits, use `io_uring_wait_cqe()` or hybrid approaches — but beware of increased latency for other tasks.

---

## 10. Quick checklist when adding peek-based handling

- [ ] Use `io_uring_peek_cqe()` for non-blocking checks.
- [ ] Always call `io_uring_cqe_seen()` after processing.
- [ ] Add short backoff to avoid busy CPU loops.
- [ ] Check `cqe->res` for errors and release buffers if needed.
- [ ] Check all relevant rings each loop iteration.
- [ ] Add termination checks (`terminate_flag`) in loops.

# io_uring_wait_cqe_timeout()

## 1. What `io_uring_wait_cqe_timeout()` does

- Waits for a completion queue entry (CQE) with a user-specified timeout.
- Blocks the caller until:
  - A completion arrives (returns 0), or
  - The timeout expires (returns -ETIME), or
  - A different error occurs (returns another negative errno).
- Useful when you want to wait for work but still bound latency with a maximum wait time.

Prototype (conceptual):
```c
int io_uring_wait_cqe_timeout(struct io_uring *ring,
                              struct io_uring_cqe **cqe_ptr,
                              const struct __kernel_timespec *timeout);
```

Return semantics:
- 0: CQE available (success) — process `*cqe_ptr`.
- -ETIME: timeout expired — no CQE within the given interval.
- other negative: real error — inspect and handle.

---

## 2. Common uses in a scanner

- ARP reply reception — wait briefly for ARP replies after sending requests.
- TCP response reception — wait for SYN-ACK / RST / other flags after sending SYNs.
- Hybrid loops where you want to wait for an event but still periodically perform housekeeping (timeouts, resubmits).

---

## 3. ARP response example

Wait for ARP reply with a timeout (pseudo-C):
```c
struct io_uring_cqe *cqe;
struct __kernel_timespec timeout_ts = {
    .tv_sec = 0,
    .tv_nsec = 200 * 1000 * 1000  // 200 ms
};

int ret = io_uring_wait_cqe_timeout(ring, &cqe, &timeout_ts);
if (ret == 0) {
    // Got an ARP reply — process
    int bytes = cqe->res;
    if (bytes > 0) {
        // Extract MAC address from ARP payload
    }
    io_uring_cqe_seen(ring, cqe);
} else if (ret == -ETIME) {
    // No ARP reply within timeout — host likely down / no reply
    mark_no_response(host);
} else {
    // Unexpected error
    fprintf(stderr, "wait_cqe_timeout error: %s\n", strerror(-ret));
}
```

---

## 4. TCP response example (tick-based loop)

Scanner pattern: send packets, then wait for replies with short ticks (e.g., 10 ms).
```c
while (!port_states.empty() && !terminate_flag) {
    struct __kernel_timespec timeout_ts = {
        .tv_sec  = 0,
        .tv_nsec = 10 * 1000 * 1000  // 10 ms tick
    };

    struct io_uring_cqe *cqe;
    int ret = io_uring_wait_cqe_timeout(&ring, &cqe, &timeout_ts);

    if (ret == 0) {
        // TCP packet received — process and acknowledge
        process_response(..., cqe);
        io_uring_cqe_seen(ring, cqe);
    } else if (ret == -ETIME) {
        // Tick expired — use this opportunity to check per-port timeouts
        check_port_timeouts();
    } else {
        // Real error
        fprintf(stderr, "wait_cqe_timeout error: %s\n", strerror(-ret));
    }
}
```

---

## 5. Tick model: short waits vs per-port timeouts

- The `timeout` passed to `io_uring_wait_cqe_timeout()` is a loop tick — not the per-port RTT timeout.
- Typical approach:
  - Use a short tick (10 ms in examples) to periodically wake and perform bookkeeping.
  - Track a per-port deadline (e.g., port-specific timeout like 50 ms or 200 ms).
  - On each tick, check whether any port's deadline has been exceeded and mark it timed out if so.

Illustrative timeline:
- Time 0: send SYN to port 80, per-port timeout = 50 ms, start 10 ms tick
- Time 10 ms: tick — 10 < 50 → continue waiting
- Time 15 ms: packet arrives — kernel wakes program immediately, process response, mark open
- Time 0..200 ms: for slow ports, multiple ticks occur until packet arrives or per-port deadline passes

This model gives:
- Prompt processing when kernel delivers a packet (no need to wait to next tick).
- Fine-grained per-port timeouts while keeping loop wakeups cheap and bounded.

---

## 6. Differences: peek_cqe() vs wait_cqe_timeout()

- peek_cqe():
  - Non-blocking memory-only check; returns immediately (0 or -EAGAIN).
  - Good for ultra-low latency polling loops and when you have other work to do.
  - Can lead to busy loops unless you add sleeps/backoff.

- wait_cqe_timeout():
  - Blocks (up to the timeout) waiting for an event — reduces spin/wake overhead.
  - Good when you can tolerate short, bounded blocking and want predictable wake intervals.
  - Combines the responsiveness of immediate wake on arrival with a bounded maximum sleep.

Choose:
- peek when you want to actively poll with custom backoff.
- wait_cqe_timeout when you prefer a simpler loop that sleeps until work or until the tick expires.

---

## 7. Handling return codes & errors

- 0: success
  - Process `cqe->res` and any user data.
  - Call `io_uring_cqe_seen(ring, cqe)` after processing.

- -ETIME: timeout
  - Normal condition — use to drive per-port timeout checks and housekeeping.

- other negative:
  - Unexpected errors. Log and take remedial action (ring reset, emergency cleanup).

Example:
```c
int ret = io_uring_wait_cqe_timeout(ring, &cqe, &timeout_ts);
if (ret == 0) {
    // handle completion
} else if (ret == -ETIME) {
    // handle tick
} else {
    fprintf(stderr, "wait_cqe_timeout failed: %s\n", strerror(-ret));
    // consider emergency cleanup
}
```

---

## 8. Pipeline and how it fits into scanning

Typical pipeline:
- Send packets → Wait for replies (wait_cqe_timeout) → Process results → Repeat

Characteristics:
- Immediate processing when kernel delivers a CQE.
- Bounded sleeps allow periodic maintenance (timeouts, resubmits, logging).
- Flexible per-port deadlines let you adapt to RTT and network conditions.

---

## 9. Practical tips & pitfalls

- Use short ticks (5–20 ms) for interactive scanning; tune based on target network RTT and CPU constraints.
- Use per-port deadlines (based on RTT estimates / configured timeouts) rather than relying on the tick alone.
- Always call `io_uring_cqe_seen()` after processing a CQE to free completion slots.
- Distinguish between tick timeouts (-ETIME) and per-port timeouts — tick just triggers a bookkeeping pass.
- Handle network errors reported in `cqe->res` (negative values) and free buffers promptly.
- On severe or repeated errors, consider draining/downscaling or performing emergency cleanup on the ring.

---

## 10. Benefits of wait-with-timeout in scanners

- Prompt processing when responses arrive (kernel wakes immediately).
- Controlled CPU usage (blocks while idle, unlike busy spin).
- Predictable ticks for timeout handling and bookkeeping.
- Works well with dynamic RTT-based timeouts and mixed network conditions.
- Improves user experience by showing results as soon as they arrive.

---

## 11. Quick checklist before using wait_cqe_timeout()

- [ ] Choose a sensible loop tick (e.g., 5–20 ms) suited to your latency and CPU budget.
- [ ] Track per-port deadlines independent of the tick.
- [ ] Distinguish -ETIME (tick expiry) vs real errors (other negatives).
- [ ] Call `io_uring_cqe_seen()` after processing each CQE.
- [ ] Handle `cqe->res` error codes and release resources promptly.
- [ ] Add `terminate_flag` checks to allow graceful shutdown.

# io_uring_cqe_get_data() 

## 1. What `io_uring_cqe_get_data()` does

- Returns the user-supplied pointer (user_data) that was attached to the SQE when it was prepared.
- Lets the application recover the exact buffer or context associated with a completed operation.
- Eliminates ambiguity about which buffer belongs to which completion → prevents leaks and simplifies resource management.

Prototype (conceptual):
```c
void *io_uring_cqe_get_data(struct io_uring_cqe *cqe);
```

Return semantics:
- Returns the same pointer previously stored via `io_uring_sqe_set_data(sqe, ptr)` (or similar).
- Use it to reclaim buffers, free context, or look up per-request state.

---

## 2. Why this matters for a scanner

Without attaching user data:
- You may send thousands of packets and lose track of which buffer corresponds to which completion.
- Leads to memory leaks or expensive global lookup schemes.

With `io_uring_cqe_get_data()`:
- Tag each SQE with the buffer pointer or a small context structure.
- On completion, recover the exact pointer and return it to the pool immediately.

Example workflow (high level):
```c
// Prepare send
char *buf = pool.acquire();
build_packet(buf, ...);
io_uring_sqe_set_data(sqe, buf);
io_uring_submit(ring);

// Later, on completion
struct io_uring_cqe *cqe;
io_uring_wait_cqe(ring, &cqe);
char *completed_buf = io_uring_cqe_get_data(cqe);
pool.release(completed_buf);
io_uring_cqe_seen(ring, cqe);
```

---

## 3. Typical scanner usage pattern

- Allocate or acquire a buffer from a pool.
- Build packet into buffer.
- Attach buffer pointer to SQE via `io_uring_sqe_set_data()`.
- Submit SQE(s).
- On completion, call `io_uring_cqe_get_data()` to get the buffer pointer.
- Release the buffer back to the pool.

This maps 1:1 between operations and buffers with zero ambiguity.

---

## 4. Minimal context struct (recommended)

Often you want more than a pointer — include a tiny context struct with whatever metadata you need:

```c
struct send_ctx {
    char *buf;
    uint16_t port;
    uint32_t seq_id;
    // ... other small fields
};

struct send_ctx *ctx = pool_ctx.acquire();
ctx->buf = pool_buf.acquire();
build_packet(ctx->buf, ...);
io_uring_sqe_set_data(sqe, ctx);

// On completion:
struct io_uring_cqe *cqe;
io_uring_wait_cqe(ring, &cqe);
struct send_ctx *done = io_uring_cqe_get_data(cqe);
pool_buf.release(done->buf);
pool_ctx.release(done);
io_uring_cqe_seen(ring, cqe);
```

Advantages:
- Single allocation for per-request state.
- Avoids expensive global maps keyed by sequence numbers or addresses.
- Cleaner and faster cleanup.

---

## 5. Conceptual kernel/kernel-user flow

- SQE: you set `sqe->user_data = your_ptr`.
- Kernel copies `sqe->user_data` to the CQE when the request completes.
- `io_uring_cqe_get_data(cqe)` returns that same pointer to userland.

Visual:
```
[BUFFER POOL]
┌─────────────┐
│ Buffer A    │  ← io_uring_sqe_set_data(sqe1, Buffer A)
│ Buffer B    │  ← io_uring_sqe_set_data(sqe2, Buffer B)
│ Buffer C    │  ← io_uring_sqe_set_data(sqe3, Buffer C)
└─────────────┘

[KERNEL SENDS]
┌──────────────┐
│ Send Port 80  │  (uses Buffer A)
│ Send Port 22  │  (uses Buffer B)
│ Send Port 443 │  (uses Buffer C)
└──────────────┘

[COMPLETIONS]
┌──────────────┐
│ Port 80 done  │  → io_uring_cqe_get_data(cqe) == Buffer A
│ Port 22 done  │  → io_uring_cqe_get_data(cqe) == Buffer B
│ Port 443 done │  → io_uring_cqe_get_data(cqe) == Buffer C
└──────────────┘

[RETURN TO POOL]
pool.release(Buffer A)
pool.release(Buffer B)
pool.release(Buffer C)
```

---

## 6. Performance benefits

- Memory efficiency:
  - Reuse a small pool of buffers (e.g., 1000) for tens or hundreds of thousands of packets.
  - Avoids per-packet malloc/free overhead.

- CPU efficiency:
  - Minimal bookkeeping on completion — read pointer, release buffer.
  - No expensive map lookups or synchronized structures if per-request context is contained in the pointer.

Example:
- Without pooling + user_data: 100k packets → 100k malloc/free operations (slow).
- With pooling + user_data: 100k packets → 1k buffers reused many times (fast).

---

## 7. Safety and best practices

- Ensure the pointer you attach remains valid until the completion arrives. Never attach stack addresses that go out of scope.
- If using contexts allocated from a pool, ensure proper lifetime and reentrancy (e.g., do not reuse until after `io_uring_cqe_get_data()` + `io_uring_cqe_seen()`).
- Consider small struct contexts for extra metadata rather than bare pointers — reduces the need for external tables.
- Check `cqe->res` for per-request success/failure before releasing resources. If `cqe->res` indicates an error, handle it appropriately (log, retry, release).
- Always call `io_uring_cqe_seen()` after processing to advance the CQ head.

---

## 8. Common pitfalls

- Attaching pointers to objects that may be freed before completion → use pools or heap allocations with controlled lifetime.
- Forgetting to release the buffer after completion → memory leak.
- Storing large objects in `user_data` directly (size is limited on some APIs); instead, store a pointer to a context.
- Assuming ordering between SQEs and CQEs — completions may arrive out of order; rely on `user_data` to find the corresponding context.

---

## 9. Quick checklist before using user_data with SQEs

- [ ] Use `io_uring_sqe_set_data()` to attach a valid pointer or context.
- [ ] Ensure the attached pointer remains valid until completion.
- [ ] Check `cqe->res` on completion before assuming success.
- [ ] Call `io_uring_cqe_get_data(cqe)` to retrieve pointer and reclaim resources.
- [ ] Call `io_uring_cqe_seen()` after processing the CQE.
- [ ] Prefer pooling contexts/buffers for efficiency and predictable lifetimes.

---

## 10. Summary

`io_uring_cqe_get_data()` is a simple but essential utility for efficient, safe, and low-overhead request lifecycle management in high-rate network scanners. It provides a direct and reliable way to associate per-request state with completions, enabling buffer reuse and avoiding expensive global state management.

# io_uring_cqe_seen()

## 1. What `io_uring_cqe_seen()` does

- Marks a completion queue entry (CQE) as consumed/seen by the application.
- Advances the CQ head so the kernel and application can reuse that slot.
- MUST be called after you finish processing a CQE; otherwise the same completion will be returned again.

Prototype (conceptual):
```c
void io_uring_cqe_seen(struct io_uring *ring, struct io_uring_cqe *cqe);
```

Effect:
- Advances the completion queue head pointer.
- Frees the CQ slot for future completions.
- Prevents repeatedly reading the same CQE.

---

## 2. Why it's critical

The CQ is a circular buffer of completions. When the kernel writes a CQE it remains at the head until the application acknowledges it. If you fail to call `io_uring_cqe_seen()` after processing:

- The head doesn't advance.
- Subsequent `io_uring_wait_cqe()` / `io_uring_peek_cqe()` calls will return the same CQE again.
- Your event loop may repeatedly process the same completion leading to infinite loops or duplicate handling.

---

## 3. Correct usage pattern

Always follow this general sequence:

1. Wait / peek for a completion
2. Inspect the CQE (check `cqe->res`, get user data)
3. Process result (log, free buffers, update state)
4. Call `io_uring_cqe_seen(ring, cqe)`

Example (blocking wait):
```c
struct io_uring_cqe *cqe;
int ret = io_uring_wait_cqe(&ring, &cqe);
if (ret == 0) {
    // 1) inspect
    void *ctx = io_uring_cqe_get_data(cqe);
    int res = cqe->res;

    // 2) handle result (check res, release buffer, etc.)
    handle_completion(ctx, res);

    // 3) acknowledge completion
    io_uring_cqe_seen(&ring, cqe);
}
```

Example (peek/poll loop):
```c
struct io_uring_cqe *cqe;
int ret = io_uring_peek_cqe(&ring, &cqe);
if (ret == 0) {
    process(cqe);
    io_uring_cqe_seen(&ring, cqe);
}
```

Notes:
- It is safe and recommended to read `cqe->res` and `user_data` before calling `io_uring_cqe_seen()`.
- Call `io_uring_cqe_seen()` even for failed operations so the queue can progress.

---

## 4. Visual representation (before / after)

BEFORE processing:
```
Completion Queue: [CQE1][CQE2][CQE3][  ][  ][  ]
                   ↑
               Next to read
```

After io_uring_wait_cqe() returns CQE1:
```
You received: CQE1
Queue still:   [CQE1][CQE2][CQE3][  ][  ][  ]
               ↑
           still points to CQE1
```

After io_uring_cqe_seen(ring, CQE1):
```
Queue now:     [  ][CQE2][CQE3][  ][  ][  ]
                 ↑
              now points to CQE2
```

Without `cqe_seen()` the head never advances and you will repeatedly see CQE1.

---

## 5. Edge cases & best practices

- Always call `io_uring_cqe_seen()` even on errors, timeouts, or when aborting a request — otherwise completions back up.
- If you return early from the processing path (e.g., due to `terminate_flag`), still acknowledge the CQE or drain the ring.
- Do not call `io_uring_cqe_seen()` on a CQE pointer that you didn't obtain from the ring — only acknowledge real completions.
- For batched processing, it's fine to call `io_uring_cqe_seen()` as you handle each CQE; you do not need to wait to acknowledge multiple CQEs at once.
- After calling `io_uring_cqe_seen()`, the `cqe` pointer should be considered invalid — do not access it afterward.

---

## 6. Common pitfalls

- Forgetting to call `io_uring_cqe_seen()` → repeated completions / infinite loops.
- Calling `io_uring_cqe_seen()` before you read `cqe->res` or `user_data` → you may lose the information needed to process the completion.
- Not acknowledging CQEs on shutdown or error paths → delayed resource reclamation and possible stalls.

---

## 7. Quick checklist

- [ ] Read `cqe->res` and any `user_data` before acknowledging.
- [ ] Call `io_uring_cqe_seen(ring, cqe)` after handling each CQE.
- [ ] Acknowledge CQEs in error/termination paths as well.
- [ ] Do not access the `cqe` after calling `io_uring_cqe_seen()`.
- [ ] Make sure loops that wait/peek for CQEs include termination checks so you can drain and acknowledge pending CQEs on shutdown.

---

# io_uring_queue_exit()

 - Used to clean up and exit io_uring rings
 - Called in multiple locations for cleanup

    Before exit:                  After exit:

## what is ring_fd (ring File Discriptor) ?
It is an notificaion path between user program and kernel

        Analogy:
          Scanner: "Hey Kernel, do these 100 packets" → Submit to SQ
          Scanner: "Now I'll sleep until you're done" → sleep() or poll(ring_fd)
          KERNEL: [Processes 100 packets...] → Finished!
          KERNEL: Rings the ring_fd BELL! 🔔 (Sends notification)
          Scanner: [Wakes up!] "Ah! ring_fd rang! Let me check results in CQ"

                            
## what  is pooling ?
It is task frequent checker used by user program side.

## step 1 (clean up process):
  - kernel marks ring as closed
  - no new operations accepted
  - completes pending operations
    
## step 2 (free shared memory):
  - unmaps the SQ/CQ ring buffers
  - return memory to system

## step 3 (close special file):
  - closes the ring_fd file descriptor

## Without cleanup (memory leak):
  - Thread 1: Creates ring (10MB) → Exits (10MB leaked!)
  - Thread 2: Creates ring (10MB) → Exits (10MB leaked!)
  - Thread 3: Creates ring (10MB) → Exits (10MB leaked!)
  - Scan 100 times → 1000MB LEAKED! 

## With cleanup (no memory leak):
  - Thread 1: Creates ring (10MB) → Exits → Frees (0MB)
  - Thread 2: Creates ring (10MB) → Exits → Frees (0MB)
  - Thread 3: Creates ring (10MB) → Exits → Frees (0MB)
  - Scan 100 times → Clean every time!
