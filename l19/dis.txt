Best near-accurate fix without hardware timestamping

Without hardware, you can't get true wire-departure time — but you can get much closer than a userspace steady_clock::now() taken before the packet even reaches the kernel. The right tool is SO_TIMESTAMPING with software flags, which makes the kernel itself stamp the packet at the moment it hands off to the NIC driver (dev_queue_xmit time) — this is the standard technique tools like ptp4l's software fallback and precise latency tools use.

Why this beats your current approach

Right now tx_ref is captured in on_pre_submit (scan.cpp ~2753) before send_tcp_packets() is even called — so it includes packet-build time, io_uring SQE setup, and submission queueing, none of which is real network latency. SOF_TIMESTAMPING_TX_SOFTWARE moves the stamp to the point the kernel's af_packet/socket layer actually pushes the frame to the driver — cutting out all of that userspace slop.

What it requires, concretely
Enable it on the send socket, once at setup:

int ts_flags = SOF_TIMESTAMPING_TX_SOFTWARE
             | SOF_TIMESTAMPING_SOFTWARE
             | SOF_TIMESTAMPING_OPT_ID;      // tags each timestamp with the SQE's ID so you can match it back
setsockopt(sock, SOL_SOCKET, SO_TIMESTAMPING, &ts_flags, sizeof(ts_flags));


After a send completes, the timestamp doesn't come back on the normal recv path — the kernel queues it on the socket's error queue. You retrieve it with a recvmsg(sock, &msg, MSG_ERRQUEUE) that pulls a SCM_TIMESTAMPING cmsg containing a struct scm_timestamping (3 timespecs; index [0] is the software one you want).
Matching it back to the right port/packet: with SOF_TIMESTAMPING_OPT_ID set, the kernel echoes back a per-socket sequence number in the error-queue cmsg (SO_EE_ORIGIN_TIMESTAMPING) that increments per send — you tag each io_uring_prep_sendmsg with that same counter and use it as the key into tx_ts_table instead of (or alongside) the current pidx-keyed pre-submit stamp.
In your io_uring architecture specifically: the clean way to fit this in without extra blocking syscalls is to io_uring_prep_recvmsg(sqe, sock, &errq_msg, MSG_ERRQUEUE) as its own persistent SQE (same pattern you already use for the ARP recv pool) — so the error-queue drain rides the same event loop as everything else, no extra thread, no extra blocking recvmsg.

This is meaningfully more plumbing than the current single steady_clock::now() line — you're adding a second per-socket completion stream to track and match up. If that's more complexity than you want right now, a much cheaper partial fix is just moving the existing tx_ref capture from before send_tcp_packets() (line 2753, in on_pre_submit) to immediately after io_uring_submit() returns inside send_tcp_packets — that alone removes the packet-construction and SQE-setup slop, and it's a one-line relocation instead of a new timestamping subsystem. It won't be as accurate as SO_TIMESTAMPING, but it's a real improvement for near-zero added complexity, and a reasonable stopgap before you invest in the error-queue approach.

Let me back up and explain the whole thing in plain terms.

The problem we're solving

Right now, when Shiva measures RTT (round-trip time) for a port, it takes a timestamp with steady_clock::now() in your own code, at the moment your code is about to hand a packet to the kernel. But there's a gap between "my code touched a timestamp variable" and "the packet actually left the network card." That gap includes:

waiting for io_uring_submit() to actually be called (packets get batched up to WINDOW size before that happens)
the kernel's io_uring worker (or SQPOLL thread) actually picking up the send

That gap gets counted as "network latency" even though it's really just your program's internal bookkeeping delay. So your RTT numbers are inflated and noisy, especially under load.

The fix

Linux can timestamp a packet itself, at the exact moment the kernel driver actually sends it (SO_TIMESTAMPING with the software-TX flag). That's a much more accurate stamp than anything userspace can produce. The catch: the kernel doesn't hand this timestamp back to you directly — it queues it on a separate "error queue" on the socket, and you have to go fetch it with a special recvmsg(MSG_ERRQUEUE) call, then match it back to the right port using a sequence number the kernel provides (OPT_ID).

So the whole patch set is really: "turn on kernel packet timestamping, then build the plumbing to collect those timestamps asynchronously and slot them into the RTT table before you use it."

What each patch actually does, in plain terms:

Includes — pulls in the Linux header definitions for the timestamping flags and error-queue structs. Housekeeping, nothing functional.
Sequence counters — Every time the kernel timestamps a send, it tags it with a number that goes up by one each time (per socket). Your code needs to keep its own matching counter so when a timestamp comes back with "this was send #47," you know which port that was for. This has to be a variable that lives as long as the socket itself does (which is the whole program run) — not something that gets reset every time a batch of hosts starts, or the numbers stop lining up.
Turn on the feature — the actual setsockopt(SO_TIMESTAMPING, ...) call that tells the kernel "please timestamp my sends and tag them with that sequence number."
A separate small mailbox for picking up timestamps — the kernel delivers these timestamps via a mechanism that needs its own little io_uring "ring" (a queue Shiva uses to talk to the kernel efficiently) to poll for them without blocking. It has to be a separate ring from the one already sending packets, because that existing ring's completion-handling code assumes every completion it sees is "a packet finished sending, free its buffer" — if we mixed timestamp deliveries into that same stream, the code would try to treat a timestamp as a packet buffer and corrupt memory.
A lookup table for "which port does this sequence number belong to" — plus a little safety tag ("generation number") so that if a timestamp arrives late — after that port slot has already been reused for a retry — we don't accidentally stamp the wrong attempt with the wrong time.
Actually assigning the sequence number when a packet is sent — right at the point in the code where a packet is handed to the kernel, tag it with the next sequence number and remember "sequence #47 = port 443."
The part that fetches and applies the timestamp — periodically check the mailbox from #4, and when a timestamp shows up, look up which port it belongs to (using #5/#6), convert it into the right time format, and store it as that port's precise send-time — overwriting the rough guess.
No change needed — once #7 writes the precise timestamp into the same table the RTT calculation already reads from, the RTT math itself doesn't need to change at all.

What "leave out fragmented packet correlation" means

Shiva can send a single logical packet as several IP fragments (when fragmentation options are turned on). Each fragment is its own separate send to the kernel. The precise-timestamp scheme needs one sequence number per actual send call — so a fragmented packet would need multiple sequence numbers, one per fragment, and then you'd need to decide which fragment's timestamp actually represents "when did this logical packet finish going out" (probably the last one).

That's extra complexity I haven't designed yet. So my suggestion is: for now, only wire up the precise kernel timestamp for normal, unfragmented packets — which is the vast majority of scans. Fragmented packets will just keep using the existing rough steady_clock timestamp, exactly like today. Nothing breaks, fragmented scans just don't get the accuracy improvement yet. It's a "ship the common case first, handle the edge case later" decision, not a bug.
